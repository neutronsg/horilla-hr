# HR 通知和报表功能范围及推荐流程

状态：Draft，待确认实施范围。更新日期：2026 年 10 月 13 日。

本方案以现有 Horilla 功能为基础。能通过现有操作或配置满足的需求直接使用；代码修改仅用于已确认的缺口。验证不等于开发，建议增强也不自动进入第一版范围。本方案已获授权实施及验证后部署；真实报销提醒由 HR 配置后启用。薪资统一入口的本地修改继续独立保留。

## 已确认的业务要求

- 报销提醒需要两种：提醒员工提交，以及提醒审批人处理待审批报销。
- 工资单由 HR 审核后手动单发或批量发送，不自动发送。
- 工资报表优先推荐现有每月 Excel，用于 HR 核对与财务交接；还没有确认需要银行文件或全新的报表格式。
- 报销下载需要明细与附件。推荐在现有报销列表和导出基础上提供一份明细加原始票据的 ZIP。
- 使用现有公司范围、HR、审批和导出访问规则，不另建独立功能权限。

| 待审批报销提醒 | 有 requested 状态、审批页面和站内通知。 | 缺少只针对仍待审批事项的定时提醒；这项需求已确认需要。 | 新增 HR 待办摘要，不建立新的报销审批体系。 |

| 报销票据打包 | 可以逐笔查看附件。 | 没有将所选明细和全部原始票据一起下载的功能。 | 增加一个明细及附件 ZIP 下载入口，保留原有逐笔查看。 |
| 工资单单发和批量邮件 | 已有发送按钮和 PDF 附件，符合手动发送方向。 | 某员工成功后会把整批 ID 标为已发送；没有明确排除草稿，且 email.send 返回 0 时也可能错误标成功。 | 保留原按钮、模板和发送方式，修复逐员工结果及草稿限制。暂不新增邮件中心或完整队列系统。 |

### 已核对的线上配置

SMTP 已配置，所有 29 名在职员工都能通过现有邮箱选择逻辑取得收件地址；其中 24 名有直属经理。没有启用通用邮件自动化或条件审批规则。现有成功邮件日志均是密码重置，不能把它当成请假和工资单邮件的验收结果。

## 推荐流程一 请假

**员工提交 → 原生邮件通知直属经理 → 经理在系统内审批 → 原生邮件通知员工结果。**

第一步确认员工的直属经理、经理邮箱以及现有审批权限。未设直属经理的 5 名员工，由 HR 确认实际审批安排，不自动指派新审批人，也不增加默认转交 HR 的规则。

对原生邮件只修复已确认的 logo 存储兼容问题。随后在受控测试收件箱验证提交、批准、拒绝和链接。如果收件人与内容已正确，就结束这项工作，不改模板、审批路由或通知架构。

**最小验收：**正确经理收到一次申请邮件；员工收到结果；logo 读取不阻断发送；链接登录后进入对应申请。验证过程中再发现的实际故障，单独记录后决定是否修复。

## 推荐流程二 报销

**员工或 HR 提交 → 现有审批列表处理 → 通过后按现有 payroll 归属日期进入工资计算。**

保持现有报销审批方式。即时提交和结果邮件尚未单独确认需要，不列为必做。若 HR 需要，优先尝试现有 MailAutomation：提交事件通知已确定的本公司 HR 收件人，状态变化通知申请员工。验证触发条件和是否重复通知；配置能满足就不改代码，仅在证明确实做不到时补对应场景。

### 必须新增的两种提醒

| 提醒 | 最小规则 | 推荐操作 |
| --- | --- | --- |
| 员工提交提醒 | 按报销周期和 HR 确认的时间，通知适用在职员工；同一提醒不重复发送。 | 邮件提醒“如有待报销费用，请在截止日前提交”，不将无报销记录等同于漏报。 |
| 审批待办摘要 | 只统计仍为 requested 的申请；有待办才发送给本公司 HR Manager 角色且具有报销审批权限的在职人员，可选择同时通知 Admin 角色。 | 建议每天最多一封，列待办数量、总额和现有处理页面链接；已处理申请不再提醒。 |

截止日、提前提醒天数及发送时间在 Settings → Payroll → Claim Reminders 配置；两类提醒默认关闭。审批收件人按本公司角色及现有审批权限解析，不维护个人名单，也不根据默认次月 6 日发薪自动确定公司的报销政策。沿用现有调度和 SMTP，仅为提醒保留必要的执行记录，防止任务重跑或重复实例重复发送。

第一版不增加强制“无报销申报”、自动拒绝迟交、自动顺延工资月份、超时升级审批、全新的多级审批或全局通知中心。

**最小验收：**只提醒适用人员；零待办不发摘要；审批后停止提醒；重复执行不重复发；暂停后不发送；不同公司的申请和收件人不混用。

## 推荐流程三 工资报表

**生成草稿 → HR 核对 → 确认 → 使用现有 Excel 交接财务 → 实际付款后记录付款日期及 Paid 状态。**

现有入口：

- [Reports → Standard Reports → Payslip Register](https://hr.neutron.sg/report/standard/payslip-register/) → Actions → Export Excel。
- 需要更多已有工资或组件字段时，先使用 Payslips 的现有详细导出及字段选择。

审核用报表选择 Draft；交接财务可选择 Confirmed；付款归档选择 Paid。金额以保存的 payslip 为准，下载不重新按员工当前薪资计算。

先给 HR 一份现有样表，核对员工、工资期间、基本工资、gross、扣款、net 和状态是否够用。若 HR 确实需要独立 CPF、SDL 或基金列，再检查详细导出是否已有；确实缺少的才补入原有导出。

**本阶段不预定开发三张新 Sheet、重新设计报表界面、成本中心、历史部门快照或银行发薪文件。**银行文件只有确认具体银行、格式和实际用途后才另立需求。

**最小验收：**HR 能找到并下载；筛选结果正确；总额与所选 payslip 一致；后改员工薪资不会改变已保存工资单的导出金额。若这些通过，这个功能可以直接交付使用，无需修改。

## 推荐流程四 报销明细和票据下载

**HR 选择公司、期间和申请范围 → 下载现有明细，或选择“明细及附件” → 取得对应 Excel 和原始票据 ZIP。**

在现有报表中补充已有字段：申请编号、员工编号和姓名、标题、描述、金额、提交时间、allowance_on、状态、已记录的审批人和附件数量。主附件与附加附件均要处理，不重复打包同一申请的同一上传；文件名包含申请编号，避免同名覆盖。

保留现有“提交时间”筛选口径。推荐增加可选择的“工资归属日期 allowance_on”口径，用于九月工资费用在十月提交的情况；不改变原默认值，也不把 allowance_on 称为实际费用发生日期。

修复已有筛选和导出中的完整性问题：结束日应包含全天，明细与汇总应覆盖完整筛选结果，不能无提示截断在 300 条。无论目前实际条数是否达到限制，都不应让导出静默给出部分对账结果。

ZIP 只包含同一筛选范围的明细和原始票据。使用现有私有存储读取接口；缺失文件在清单中明确列出。沿用现有 HR 和导出规则，不把附件变成公共链接。先按当前团队规模提供有明确容量限制的下载，未证实需要大文件后台任务前不引入新任务中心。

**最小验收：**所选申请与附件一一对应；主附件和附加附件都可下载；同名文件不覆盖；缺失文件有说明；日期边界及超过 300 条的测试正确；未授权用户不能导出其他公司的数据。

本阶段不添加审批时间字段、实际费用日期、费用类别、项目、成本中心、独立报销已付款状态或 PDF 票据合并。Approved 保持“已审批”的含义，不当作“已付款”。

## 推荐流程五 工资单邮件

**HR 审核 → Confirmed 或 Paid → 使用原有单发或批量 Send via mail → 检查逐员工结果 → 仅重发失败项目。**

按业务节奏，建议实际发薪后发送；如 HR 需要提前发已确认工资单，仍可手动操作。发送不改变付款状态，不产生银行转账。

只做现有功能的必要修复：

1. 服务端排除 Draft 和 Review ongoing，不能仅靠 HR 自觉或隐藏按钮。
2. 每位员工只收到自己的现有 PDF，沿用原有邮箱选择逻辑。
3. 检查 email.send 的实际结果，仅更新本次成功发送的员工所对应的 payslip ID。
4. 部分失败时，成功项目保持成功、失败项目保持未发送；利用既有邮件日志或轻量逐项结果让 HR 知道哪些需要重试，不只显示“处理中”。

原有模板、发件配置、PDF、单发与批量按钮优先保留。实际 SMTP 验收已发现 HR 账号私人邮箱作为工资单 From 身份被服务商拒绝，因此沿用已验证的 SMTP 配置发件地址，HR 邮箱保留为 Reply-To。链接或重复发送等其他问题仍只在实际验证出缺口后补修。不要为了这些尚未验证的问题预先换发件机制或建新预览页面。

**最小验收：**单发正常；三名员工中一人失败时只标记两人成功；返回 0 不标成功；草稿不能发送；重试选中失败者不再发送成功者；金额与已审核工资单一致。

暂不开发完整持久队列、模板或 PDF 版本系统、自动重试、已读追踪、收件箱送达追踪、重发原因流程或自动发送。若实际批量发送出现中断丢失等问题，再提出有证据的增强需求。

## 最小实施清单与顺序

| 类别 | 工作 | 进入开发的条件 |

| 配置和验收 | 请假经理配置、业务邮件测试、工资 Excel 样表、现有报销事件自动化。 | 先执行现有流程；通过就不改代码。 |
| 已确认修复 | 请假 logo 读取；工资单批量成功标记、返回 0 和草稿限制；报销导出 300 条限制及结束日边界。 | 问题已由代码及线上存储核对确认，按小范围修复。 |
| 确需新增 | 两种报销定时提醒；报销明细的必要现有字段与票据 ZIP。 | 业务需求已明确；提醒时间、收件人和下载字段确认后实施。 |
| 条件性补齐 | 自动化触发或收件规则、工资报表缺列、发件身份、链接或重复发送。 | 现有配置或业务测试证明确实不能满足后，单列具体 gap。 |
| 暂不做 | 多级审批路由改造、工资报表重建、银行文件、通知中心、通用邮件队列及其他扩展。 | 当前无明确需要；以后有实际使用问题或新业务要求再评估。 |

建议先验证现有功能并修复已确认错误，再做两种提醒和票据包。工资报表可以先交给 HR 使用，不应等待新功能完成。

## 尚需确认的业务信息

1. 未设直属经理的 5 名员工实际如何审批请假。
2. 报销提交截止日、提醒时间，以及待审批摘要的现有 HR 收件人。
3. HR 看过现有工资 Excel 后，具体缺哪几列；若没有缺列，不开发工资报表改动。
4. 报销明细的最低字段，以及是否采用建议的 Excel 加原始票据 ZIP。
